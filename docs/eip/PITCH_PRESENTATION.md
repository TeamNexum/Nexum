## SLIDE 2 — Le problème

**Titre :** Un environnement numérique fragmenté et chronophage.

**Contenu clé :**
- Setup éclaté : launchers de jeux, logiciels constructeurs (Razer, Corsair…), utilitaires système isolés.
- Temps perdu avant **chaque** session (jeu, stream, travail).
- Solutions actuelles **verrouillées à une marque** (Razer Synapse, Corsair iCUE) ou **trop techniques** (scripts AutoHotkey).
- **Zéro automatisation contextuelle** : rien ne s'adapte tout seul à ce que je fais.

**Note orale :**
> « Le vrai problème, ce n'est pas un logiciel manquant, c'est la fragmentation. Mon clavier a son appli, ma souris une autre, mes lumières une troisième, mes jeux un launcher chacun. Aucun de ces outils ne parle aux autres. Les solutions existantes sont soit enfermées dans une seule marque, soit réservées à ceux qui savent écrire des scripts. Le grand public reste sur le carreau. »

## SLIDE 3 — La solution : Nexum

**Titre :** Un clic, un « mode », tout votre setup s'aligne.

**Contenu clé :**
- Application **universelle, no-code et agnostique** de bureau.
- Notion centrale : le **« Mode »** (Ranked, Direct, Chill…) qui synchronise en un clic : logiciels, système, périphériques, objets connectés.
- **Agnostique** : connecte des marques concurrentes entre elles.
- **No-code** : on crée un mode sans écrire une ligne de code.
- **Contextuel** : les modes peuvent se déclencher tout seuls (heure, app lancée…).

**Note orale :**
> « Nexum introduit le concept de "mode". Un mode, c'est votre intention : "je veux jouer en ranked", "je lance mon direct", "je me détends". Vous cliquez, et Nexum orchestre tout : il lance vos jeux, règle le son et l'écran, allume vos lumières dans la bonne ambiance, ferme ce qui gêne. Le tout sans script, et sans être prisonnier d'une seule marque. »

## SLIDE 11 — Ce qu'on a construit (architecture, vulgarisée)

**Titre :** Une architecture pensée pour le no-code et la sécurité.

**Contenu clé :**
- Idée directrice : **tout est une Action typée**, exécutée par un **Adapter** de plateforme, orchestrée par un **Engine**, à partir d'un **modèle de Mode déclaratif (DSL JSON)** partagé.
- Conséquence n°1 : **no-code** — un mode = des données, jamais du code.
- Conséquence n°2 : **Marketplace sûre** — un mode partagé ne contient aucun code exécutable (allowlist + score de risque).
- Conséquence n°3 : **cross-platform & IA** « gratuits » (l'IA ne produit que ce JSON validé).
- Stack : React/TS + **Tauri 2 (Rust)** en desktop ; **axum + PostgreSQL** en cloud ; **offline-first** (SQLite).

**Note orale :**
> « Un mot sur nos choix techniques, car ils portent toute la promesse produit. Chez nous, un mode n'est jamais du code : c'est de la donnée déclarative. Cette décision résout d'un coup quatre problèmes : le no-code, la sécurité de la Marketplace — puisqu'on ne partage jamais de code exécutable —, le multi-plateforme, et l'IA, qui n'a qu'à produire cette donnée. Le cœur est en Rust pour la performance et la sécurité mémoire. »

## SLIDE 15 — Analyse de risques (SWOT condensé)

**Titre :** On connaît nos risques, on les adresse.

**Contenu clé :**
- **Dépendance API tierces** → Adapters isolés + dégradation propre (`on_error`) : si une API tombe, le reste du mode marche.
- **Anti-cheat** → jamais d'injection dans les jeux ; uniquement des API/SDK officiels (`steam://`).
- **Réaction des OS** (profils natifs Windows) → notre valeur est l'orchestration cross-marque + IA, pas un simple profil.
- **Volume de dev** → architecture par Adapters = ajout incrémental, on priorise 4-5 intégrations démontrables.

**Note orale :**
> « On a une lecture lucide de nos risques. Le principal, c'est la dépendance aux API tierces : on l'a désamorcé par conception, chaque intégration est isolée et un mode continue de fonctionner même si une brique tombe. Sur l'anti-cheat, on ne s'injecte jamais dans les jeux, on n'utilise que des protocoles officiels. Et notre architecture par adapters nous permet d'ajouter des intégrations progressivement, sans réécrire le cœur. »

# Script de démo live (Greenlight juillet 2027 — AUCUNE vidéo autorisée)

> Objectif : démontrer, sur **machine réelle** + **lampe Philips Hue physique**, que le produit **fonctionne en direct**. Prévoir un **filet de sécurité** (voir plan B) car le jury est en présentiel.

## Préparation matérielle (avant d'entrer)
- 1 PC de démo (Windows, OS prioritaire) avec Nexum installé (**installeur signé**, pas un `cargo run`).
- 1 **pont + ampoule Philips Hue** posés visiblement sur la table du jury (effet « waouh »).
- Un **hotspot / réseau maîtrisé** (ne pas dépendre du Wi-Fi de la salle) pour la sync cloud et la Hue.
- Un **2e appareil** (téléphone) appairé au même compte pour la démo mobile + sync.
- Steam installé + un jeu léger installé (lancement rapide).
- Slack (ou une app témoin) ouvert pour montrer sa fermeture.
- Comptes de démo pré-créés ; modes de secours déjà importés.
- **Répétition chronométrée** faite au moins 2 fois la veille.

## Déroulé (viser 12-15 min)

**Scène 0 — Contexte (30 s).**
> « Voici Nexum installé sur cette machine. Sur la table, une vraie lampe Hue. Tout ce que vous allez voir est en direct. »

**Scène 1 — Créer un mode en no-code (~3 min).**
1. Ouvrir l'éditeur de modes.
2. Créer un mode « Ranked » depuis le catalogue d'actions (glisser des steps) : `audio.set_volume 70%`, `display.set_brightness 100%`, `system.close_app Slack`, `iot.hue.activate_scene`, `gaming.launch_steam`.
3. Souligner : « Je n'ai écrit **aucune ligne de code**. Ce mode est juste de la donnée. »

**Scène 2 — Activer le mode → actions réelles (~3 min).**
1. Cliquer « Activer Ranked ».
2. Montrer **en temps réel** dans le LiveActionsPanel chaque step qui passe au vert.
3. Effets **physiques observables** : le volume système change, la luminosité change, **Slack se ferme**, **la lampe Hue change de couleur devant le jury**, Steam se lance.
4. Insister : « Chaque coche verte est une action réellement exécutée sur le système, pas une animation. »

**Scène 3 — Automatisation contextuelle (~2 min).**
1. Montrer une règle « Mode Chill si heure ≥ 18h » (persona Sarah).
2. Pour la démo, déclencher via une règle horaire réglée à l'instant présent (ou un trigger équivalent).
3. Le **Mode Chill** s'active **tout seul** : lumières tamisées, ambiance changée.
> « Personne n'a cliqué. C'est le contexte qui a déclenché le mode. »

**Scène 4 — Sync cloud + télécommande mobile (~2 min).**
1. Sur le **téléphone**, activer un mode → il s'exécute sur le PC (télécommande via cloud).
2. Montrer qu'un mode créé sur une machine est **retrouvé sur l'autre** (sync).

**Scène 5 (bonus, si stable) — IA Mode-as-Code (~2 min).**
1. Taper une phrase : « Crée-moi un mode stream : lance OBS, coupe les notifications, mets une ambiance violette. »
2. Montrer le **JSON de mode généré**, validé (simulation `validate()`), puis proposé à l'activation.
> « L'IA n'a produit que de la donnée déclarative validée — jamais du code. C'est notre garde-fou de sécurité. »

**Clôture (30 s).**
> « Créer sans coder, exécuter du réel, automatiser, piloter à distance, et générer par IA — le tout en direct. »

## Plan B (résilience démo live)
- Si la **Hue** échoue : basculer sur les effets système (audio/écran/apps) déjà probants ; montrer les logs d'exécution.
- Si le **réseau** échoue : Nexum est **offline-first** — insister dessus (« ça marche même sans réseau ») et faire la démo locale ; garder la sync pour la fin.

# Questions probables du jury + éléments de réponse

**Q1 — En quoi êtes-vous vraiment différents de Razer Synapse ou Corsair iCUE ?**
> Ils sont **verrouillés à leur propre matériel** et ne font aucune orchestration système/logiciel/IoT cross-marque. Nexum est **agnostique** : il fait dialoguer des marques concurrentes, plus le système, les jeux et la maison connectée, le tout en **no-code**. Aucun concurrent ne réunit les quatre (voir tableau slide 8).

**Q2 — Windows intègre déjà des profils. Ne risquez-vous pas d'être court-circuités par l'OS ?**
> Un profil OS ne pilote ni les lumières Hue, ni le RGB SteelSeries, ni le lancement de jeux, ni les automatisations contextuelles cross-marque. Notre valeur est l'**orchestration universelle + IA**, pas un réglage système. C'est un risque identifié (slide 15) qu'on adresse par la profondeur d'intégration.

**Q3 — Comment évitez-vous d'être détectés comme un cheat par les anti-cheat ?**
> On **n'injecte jamais** dans les processus de jeu. On n'utilise que des **API et SDK officiels** (`steam://`, SDK constructeurs). C'est documenté et c'est une contrainte d'architecture, pas une option.

**Q4 — La Marketplace, ce n'est pas un vecteur de malware (on exécute du code d'inconnus) ?**
> Non, et c'est notre plus grande force de conception : un mode partagé **n'est que du JSON déclaratif**, jamais du code exécutable. La validation = **allowlist d'action_types** + validation des params par les adapters + **score de risque IA** + modération + réputation créateur. C'est structurellement plus sûr qu'un système de plugins.

**Q5 — Votre IA génère du code exécuté sur ma machine, c'est dangereux non ?**
> L'IA ne génère **jamais de code**. Elle produit uniquement le **DSL déclaratif** (le même JSON que l'éditeur no-code), qui passe par la **simulation** (`validate()`) et la vérification de capacités **avant** toute exécution. Le LLM n'a aucun accès direct au système.

**Q6 — La consommation CPU/RAM ? Un utilitaire de plus qui rame en fond ?**
> Cœur en **Rust**, architecture **event-driven** (pas de polling permanent), desktop **Tauri** (empreinte bien plus légère qu'Electron). La performance est un argument de vente, pas une contrainte subie.

**Q7 — Comment allez-vous acquérir des utilisateurs (go-to-market) ?**
> Trois leviers : la **Marketplace** (chaque créateur de mode populaire nous fait de la pub), les **influenceurs Twitch/YouTube** (notre cible y vit), et l'**effet démonstratif** (les modes IoT sont visuellement viraux). Coût d'acquisition faible parce que le produit se montre tout seul.

**Q8 — Le freemium à 4,99 €, est-ce soutenable ? Où est l'argent ?**
> Trois sources cumulées : abonnement SaaS, licence lifetime pour les anti-abonnement, et **commission Marketplace** (marge élevée, sans coût de production côté nous). Le B2B (salles e-sport, entreprises) vient s'ajouter. Voir KPIs et projections (slide 14).

**Q9 — Avez-vous vraiment validé le marché, ou est-ce une intuition ?**
> **15-20 interviews** sur nos trois personas + **2 cycles d'itération** avec des bêta-testeurs. Conclusion : **consolidation** (concept validé), pas pivot. Trois enseignements exploités : douleur du temps de prépa confirmée, effet waouh IoT, no-code indispensable (slide 9).

**Q10 — Que se passe-t-il si une API tierce (Steam, Hue) change ou tombe ?**
> Chaque intégration est un **Adapter isolé**. Le champ `on_error` (continue/abort) permet une **dégradation propre** : si la Hue tombe, le reste du mode s'exécute quand même. On ne dépend jamais d'une seule brique pour que l'expérience fonctionne.

**Q11 — Quelle est la barrière à l'entrée / qu'est-ce qui vous protège d'un gros acteur ?**
> Le **fossé technique** (architecture DSL + adapters + Marketplace sûre non triviale à répliquer), l'**effet réseau** de la Marketplace, et le positionnement **neutre/agnostique** qu'un fabricant de hardware ne peut pas adopter sans se renier.

**Q12 — Est-ce réellement déployable, ou juste une démo ?**
> Le produit du Greenlight est **déployé** : installeurs **signés** Windows et Linux, cloud en ligne, offline-first. Ce que vous voyez tourne sur une machine réelle, pas un environnement de dev — c'est l'exigence même du Greenlight (démo live obligatoire).

**Q13 — Cross-platform : est-ce que tout marche vraiment sur Linux et Windows ?**
> Le **cœur est OS-agnostique** et testé en CI ; seuls les **Adapters** ont du code spécifique OS (`#[cfg]`). Les actions de base (audio, écran, process, launch) sont implémentées **des deux côtés**. macOS est un bonus post-EIP.

**Q15 — Et la conformité RGPD / la vie privée ?**
